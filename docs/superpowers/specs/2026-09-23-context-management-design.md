# 单 Agent 长上下文管理设计

日期：2026-09-23。状态：已按用户确认的策略实施；验收记录见 [上下文管理实现与验证](../../context-management-2026-09-23.md)。

用户确认的约束：不能以丢弃消息解决上下文超长。摘要与归档方案继续细化，删除式滑动窗口及其兼容/失败降级路径排除在设计之外。

代码基线：`refactor/standalone-agent-20260923` / `3d975ff48daf6938b75afbdc8386824f25121588`。用户工作目录交付文件与该版本已核对。本方案只涉及单 Agent，不重新引入 Group 或前端。

## 1. 结论与取舍

推荐第一版采用：**完整请求预算检查 + 安全边界内的前台增量摘要 + 近期原文 + 压缩原文附件 + 有界超限恢复**。

必须满足：历史消息退出模型工作集之前，原文已可靠归档，且其任务信息由摘要承接；大工具结果改为预览之前，已有可读取的原文引用。不允许按条数或 token 数直接删除旧消息，也不允许在摘要失败、容量未知或存储不足时回退到消息丢弃。摘要会损失细节，因此原文可查回是基础能力，不能作为可选增强；这不要求每次模型请求携带全部历史原文。

“前台”指 Agent 暂停下一次推理，等待压缩完成再继续；异步入口仍使用可取消的异步 I/O，并不阻塞整个应用的事件循环。这是本草案的默认建议，未把后台压缩的额外并发状态引入一期。

| 方案 | 性能与成本 | 实现与维护 | 长任务可用性 | 判断 |
| --- | --- | --- | --- | --- |
| 按 token 丢弃旧消息 | 无摘要调用、延迟小 | 最低，但仍需正确切分工具批次 | 早期目标、决策和失败经验容易消失 | **已排除，不提供兼容或降级模式** |
| 前台增量摘要 + 近期原文 + 归档 | 普通回合无额外网络调用；压缩时增加调用与等待 | 中等，可复用当前运行所有权、超时和共享状态机 | 能持续推进，并查回被压缩材料；摘要仍可能失真 | **推荐一期** |
| 后台摘要 + 检索记忆系统 | 可能隐藏部分等待；会有过期摘要、重复计算与索引成本 | 高，需要并发提交、追赶策略、检索和质量评估 | 适合后续跨会话任务；不能替代基本预算控制 | 后置 |

没有实测依据证明摘要能降低本项目总成本：它减少后续输入，但增加摘要费用、等待时间，并可能降低提示词缓存命中。先建立观测，再决定是否采用便宜的独立摘要模型或后台执行。

## 2. 设计时的项目基线与接入缺口

| 当前实现 | 对设计的影响 |
| --- | --- |
| `core/agent_runtime/turn_machine.py` 为同步、异步、流式、非流式提供同一回合策略 | 在这里统一决定何时压缩；不要在四个入口各实现一套 |
| `runtime.py` 在新输入和工具回合后按消息条数裁剪 active | 必须移除运行路径中的这类裁剪，统一通过摘要与归档更新工作集；不保留旧策略开关 |
| `context.py` 的 `ContextTransform` 是同步、脱离原对象的投影函数 | 保留为无 I/O 的投影接口；不要偷偷在里面调用模型 |
| `Session.active` 的 80 条是按完整用户回合保留的软限 | 同一用户请求下几十轮工具执行可以持续增长；必须允许在用户回合内部压缩 |
| `Session.history` 默认硬限 1000 条 | 是近期缓存，不能当作永久完整记录或恢复来源 |
| `LLMProviderConfig` 只有输出 `max_tokens`，没有窗口容量 | 必须显式配置容量或注入可信元数据；不能把输出上限当上下文上限 |
| `payload.py` 会过滤独立 reasoning；工具 schema 与消息分开构建 | 计数对象必须是最终实际请求，包括 schema、参数和协议开销 |
| `llm.py` 仅记录非流式 usage，SSE 丢弃 usage-only 帧 | 补齐流式用量，且区分请求输入占用与累计账单 |
| `session_store.py` 是严格 v1、idle 时手动保存的快照 | 新增 v2 保存压缩状态；不因此声称已有崩溃自动续跑 |
| 工具已有字符、字节上限 | 这些限制保护内存，不能保证适合任意模型窗口 |

## 4. 模块职责和执行流程

推荐新增小型 `core/agent_runtime/context_management/` 包，内部区分预算、纯策略和摘要执行；现有 `context.py` 继续处理投影与工具配对校验。

| 单元 | 职责与边界 |
| --- | --- |
| `ModelBudget` / `TokenCounter` | 描述容量、输出预留、计数方法；对最终请求给出带可信度的估计 |
| `ContextPolicy` | 纯计算：是否压缩、选择哪些原文、如何保留尾部、如何处理大结果；不调模型、不改 Session |
| `ContextSummarizer` | 用已预算的源材料生成候选摘要，提供同步/异步调用；不提交会话 |
| `Session` / `SummaryCheckpoint` | 管理消息身份、工作集和压缩提交；不读取环境变量、不拥有模型客户端 |
| `CompactionArchiveStore` | 保存被替换材料、按身份分页读取，管理配额；不驱动 Agent 或重放工具 |
| builder / service / CLI | 解析配置、注入依赖、保持生命周期所有权，展示状态和手动操作 |

共享回合状态机在每次主模型请求前执行：

```text
构建实际请求 → 预算检查
  ├─ 适合发送 → 主模型调用 → 完整工具批次 → 下一次检查
  └─ 需要压缩 → 规划源材料和保留片段
               → 生成并验证摘要候选
               → 写入原文附件
               → 核对身份/版本并发布 checkpoint
               → 重建、复核请求 → 主模型调用
```

在 `Step` 协议中增加 `CompactionRequest(plan)`，返回独立候选结果；状态机负责规划、验证和提交规则，driver 只负责同步或异步 I/O。摘要即使在流式运行中也按非流式请求执行，不把摘要文字混入给用户的答案。

明确的模型超限错误通过 generator 的 `throw` 通道回到同一策略节点，携带请求 ID 和 `main/summary` 阶段，不能由 driver 自行重启整个 `run`；正常返回值继续表示消息或摘要候选。仅主推理超限进入一次压缩后重试；摘要请求超限在本次 CompactionRequest 的调用额度内处理或失败，绝不再次进入嵌套压缩恢复。

压缩只发生在没有未配对工具调用的安全边界。摘要调用不消耗业务工具回合，但纳入原运行的 deadline、取消和资源清理；每个业务回合至多一次主动压缩和一次超限恢复。同步自定义客户端不可中断的问题仍受原有接口限制，不能用摘要功能承诺硬抢占。

## 5. 预算与触发规则

对于共享输入输出窗口的模型：

```text
C = 配置或可信元数据给出的上下文容量
O = 本次请求的有效最大输出预算
S = 协议与计数误差余量
B = min(可选的独立输入上限, C - O - S)
P = 最终发送请求的输入 token 估计
```

没有独立输入上限时，忽略 `min` 的第一项。输入输出限制分离、推理 token 有特殊计费或容量规则的模型，由适配器计算 `B`，不强行套用同一公式。配置不允许 `B <= 0`，也不静默缩小用户明确设置的输出上限。

建议初始软触发点为 `P > 0.80B`，压缩目标为 `P' <= 0.55B`，`P > B` 必须先处理再发送。触发点与目标之间留出距离，避免每轮压缩。它们是待评估的初值；保护内容较多时可以放宽软目标，但不能放宽硬预算。

实施补充：服务端明确报超限时，额外增加 `0.10C` 余量，并把保留目标收紧为 `min(0.55B, 0.50P)`，避免本地低估时仍保留全部旧材料。最新用户原文和必要完整批次继续受保护；没有可压缩材料时明确失败，不原样无限重试。

`S` 的初值建议：使用匹配 tokenizer 时取 `max(256, ceil(0.05C))`；只有估算时取 `max(512, ceil(0.10C))`。这些余量不是数学上的适配保证。中文、代码、JSON、emoji、工具参数必须纳入校准样本；默认启发式不得简单采用字符数除以四。计数失败不能返回零。

上下文管理统一使用预算检查与摘要归档，不提供 `legacy` 丢弃模式。模型容量必须来自显式配置或可信元数据；旧配置缺少该值时，提示补充容量并暂不启动新的模型推理，保留已有会话，允许查看和保存。用户只需补充窗口容量，不要求理解全部高级参数。不根据任意模型别名猜测 128K，也不靠反复撞超限来发现容量。旧 `active_message_limit` 不再触发裁剪，迁移时明确提示其原行为已移除。

计数包括：当前 system/rules、摘要、最新用户原文、保留的工具调用及结果、工具定义和协议封装。若以后支持响应 schema，也必须包括。先运行 `ContextTransform` 再计数，并发送同一份脱离会话的请求快照；压缩后重建一次投影并重新计数。投影函数须稳定且无副作用，不能在计数和发送间偷偷扩展输入。

第一版可对有界工作集完整估算，不先做复杂的增量 token 缓存。按后续测量决定是否缓存工具 schema、固定规则和不可变 entry；缓存不得随整个历史无限增长。usage 只校准对应请求，不能把旧摘要前的占用值拿来判断新视图。

## 6. 摘要内容、保留边界和巨大输入

模型工作集由以下内容组成：当前应用 system/rules、带来源标识的历史摘要、近期原文，其中最新用户请求必须保留且只出现一次。最新用户请求在历史中较早时，规划器保留它作为当前任务锚点，并将其后的早期执行过程压缩；原文尾部保持原顺序。

摘要建议使用有上限的结构化文本，固定包含：任务目标与用户约束、已完成事项、进行中与阻塞项、关键决策及理由、相关文件/资源、已验证结果与失败尝试、下一步、来源归档 ID。摘要是历史材料，不能把工具输出中的指令提升成 system 权限。它也不能保证自动识别并无损保留任意自然语言约束；关键材料可查回原文。

增量方式是“上一份摘要 + 此次新增需折叠材料 → 下一份摘要”，不每次重新读取全部归档。摘要长度上限建议为 `min(4096, floor(0.10B))` token，并取不超过模型有效输出能力的值，显式作为摘要请求的输出参数，不能直接继承主推理的 `max_tokens`。小窗口若连必要结构和保护原文都容不下，应报告容量不足。

切分基本单位是完整 assistant 回复，以及 assistant tool-call 批次连同全部对应 results。保留最近的完整执行片段，并优先保留最近一批工具结果；可以压缩同一用户回合内更早的完整片段。禁止只留下工具结果、只留下半个批次或修改调用参数来凑预算。

最近片段是软偏好，不能凌驾于容量。若必要原文使 `0.55B` 无法达到，可在满足硬预算且至少减少 `max(128, ceil(0.10B))` token 时接受；这个最小进展值同样是待评测的初值。当必要内容已接近触发点且没有足够可压缩前缀时，跳过无意义的主动压缩，显示空间紧张。成功但仍高于软触发点时，记录本次源边界、占用和可压缩材料量；在新增可压缩材料至少达到 `0.10B`、新用户请求或手动请求出现之前，抑制再次主动尝试。仅 revision 变化不会解除抑制；硬预算检查始终执行，并绕过软抑制，不能原地重复压缩同一材料。

大输入分别处理：

- **最新用户请求本身过大：**不静默截断指令，返回具体的 `InputTooLarge` 及分段/文件输入建议。独立文档摄取不属于旧历史压缩。
- **system 或工具定义过大：**报告固定开销及缺口，要求减少配置或使用更大窗口；不压缩安全规则，不悄悄移除工具。
- **工具结果过大：**保留工具 ID、状态和批次结构，把上下文中的正文缩为有界预览并带归档引用。归档保存 runtime 实际拿到的结果，成功写入后才发布引用。多个结果共享一批总预算，不能每个结果各占全部额度；连最小结果封装都放不下时明确失败。
- **工具参数或不可拆分批次过大：**可压缩更早的完整批次；仍无法容纳必要最近片段时返回明确诊断，不改变参数、不重执行工具。

现在终端在每个管道超过约 80KB 后已丢弃部分输出，通用结果也在约 65Ki 字符处截断。本文归档保证的是“压缩或预览替换前会话可见的内容”，不是工具完整原始输出。完整 stdout/stderr 留存需要在管道读取处另做有配额的流式落盘，列为后续增强。

摘要调用自身也要符合预算：单独计算 `B_summary = C_summary - O_summary - S_summary`，有独立输入上限时再取较小值；请求包含摘要指令、上一摘要和源材料封装，合并请求还必须计入全部参与合并的中间候选。超长来源按合法片段顺序生成中间候选，单次压缩最多 4 次摘要调用，包含最终合并、缩写修复以及摘要超限后的再调用；单个大正文仅可作为标明来源的引用数据分段。每次必须有进展；全部候选完成和校验前不发布部分 checkpoint。预算内不能完成则保持旧工作集并报告失败，不无界递归“摘要的摘要”。

## 7. 身份、归档与提交一致性

新增内部 `SessionEntry` 包装，以不可变 `entry_id` 标识消息，包含原 Message 和必要来源信息。Session 增加 `session_id`、`revision`；运行时另有 owner/generation。工具调用 ID、文本相等和数组下标都不能替代消息身份。

`SummaryCheckpoint` 至少保存 checkpoint ID、前一 checkpoint ID、本次新增覆盖的 entry IDs、保留 entry IDs、摘要文本/格式版本、archive 引用、计数方法及前后估计。旧链只保留父引用，不把历次内容和 ID 集合不断累加到当前 checkpoint。内存 entry 表保留 history 与 active 的并集；不再被二者引用的旧材料和链元数据从归档按需读取。此元数据不直接变成新的 provider 消息角色。

大工具结果预览属于 `WorkingView`：用 `entry_id → preview + archive_ref` 的投影覆盖表替代请求中的正文，原始 entry 不变，工具参数和结果身份不变。只做预览替换时不必调用摘要模型，但仍先归档、校验预算，再原子提交视图版本。快照保存这张覆盖表；后续摘要知道该片段是预览，必要时按预算读取归档，不能当作完整观察。覆盖表的键只能指向仍在 active 的 tool-result entry，只覆盖正文；折叠或移除 entry 时同步清理覆盖项。新增、替换或清除覆盖项都递增 revision。

所有正式会话修改经过受控方法递增 revision，包括新增消息、换 system、clear、load 和 reset。逐步撤销内部直接修改公开 list 的写法；外部原地修改 Message/list 仍属不支持，不能声称 revision 能发现任意旁路篡改。reset 必须从 checkpoint 与保留工作集重建，不能把 history 缓存直接全部塞回 active。clear/new 仅由用户主动发起，不能作为自动超限恢复手段。

事务顺序：

1. 持有当前运行所有权，拍下身份、revision、源 entries 和旧 checkpoint 的脱离对象视图。
2. 预算、摘要与校验都在候选上进行。摘要必须非空、正常结束、无工具调用、长度合格；重建请求必须工具配对完整且满足硬预算。
3. 将准确被替换的 entries、旧摘要、旧归档链和 schema 写为不可变附件；不能只保存经过截短的摘要 prompt。使用临时文件、校验、fsync 和原子改名；需要承诺断电耐久时同时处理目录 fsync。
4. 在运行 owner 内检查取消/deadline、session/generation、revision 与源边界，再无 `await` 发布 checkpoint、active IDs 和覆盖表组成的完整 WorkingView。仅用短锁保护提交，不能持 `threading.RLock` 跨 `await` 充当任务锁。

失败或取消不发布候选；此前已正常提交的用户输入与工具结果保留。附件写入者没有修改 Session 的权限，取消后迟到的写入最多留下未引用文件。崩溃留下附件并不等于内存会话已被持久保存。

第一版用普通不可变归档文件即可，无需 SQLite、向量库或全框架事件溯源。归档目录由应用管理，置于受控私有状态目录，通过 session ID 隔离；opaque ID 由运行时生成。配置总字节配额，临时文件和未引用文件也计入；满额时拒绝本次压缩或结果替换。一期只清理能确定未发布的临时/失败附件，不自动回收成功发布过的归档，因为当前覆盖表、旧 checkpoint 链和已保存快照都可能仍引用它；不能仅凭当前 checkpoint 判断可删除。

提供 `read_context_archive` 只读分页工具，接受当前会话内的归档 ID、entry ID/分页游标与有界页大小，不接受任意文件路径；校验归档身份与读取上限，返回稳定来源与续读游标。它返回历史材料，不执行历史调用。摘要保留来源链，用户和 Agent 都能按需找回材料；第一版不提供跨归档语义检索。

这不是每次事件都立即落盘的完整 transcript：用户主动 clear、旧版本已经丢失的内容，以及源头未捕获的输出，不在追溯承诺内。内存 history 可以作为限长缓存，但逐出缓存不能删除某条消息的最后一份原文：必须确认原文仍完整保存在 active，或已可靠归档；否则先归档，失败则停止清理并报告资源问题。history 专有消息也适用此规则，不能绕过它依靠现有硬裁剪。缓存清理放在安全边界，必要时允许当前完整工具批次暂时超过缓存条数目标；归档失败不能阻止记录已完成工具的结果。active 只通过摘要与归档机制缩减，不再靠条数先行丢弃。

## 8. 持久化与兼容

v2 快照自包含 session 身份、revision、entry 表、history/active ID 列表、当前 checkpoint 和 WorkingView 覆盖表。history 与 active 引用的并集都要保存，不能假定 active 是 history 的子集。保留严格 schema 校验、工具配对校验、私有权限和原子文件替换；工具状态/结果来源元数据须明确编码。

读取 v1、写出 v2。v1 的 history/active 已分别解码且缺少稳定身份，迁移不能依据相同文本或当前 `Message.__eq__` 合并消息；只有完整编码和顺序能唯一对应时才复用身份，歧义保留独立导入 ID。迁移明确标示历史覆盖不完整。

归档附件不内嵌进不断增大的快照。快照保留自包含摘要和尾部以便检查，但恢复执行同时依赖其引用的归档；缺附件时允许打开会话检查和报告缺失，补齐前不自动继续推理，不能静默降级为仅剩摘要的会话。history 专有材料归档时也必须留下可持久恢复的引用，可放在会话归档清单中，按需分页读取，不把全量清单常驻内存。若以后提供便携导出，再加入携带附件的 bundle。load 使用当前应用指令，不能把旧 system 自动提升为当前配置。

维持 idle 时手动 save/load 的产品语义；手动压缩占用与 run 相同的所有权槽，自动压缩复用当前槽。加载或读取任何记录都不重放工具，也不承诺崩溃后 exactly-once 执行。

## 9. 超限与失败行为

| 情况 | 行为 |
| --- | --- |
| 模型容量未知、必要归档缺失或存储不足 | 保留现有消息，说明缺失配置/资源；不能退回滑动窗口、自动清空或无归档截断 |
| 主动压缩失败，但旧请求仍在硬预算内 | 保持原工作集，提示失败，本回合允许继续一次；在新增可压缩材料至少达到 `0.10B`、出现新用户请求、用户手动重试或达到硬限制之前，抑制重复主动尝试 |
| 必须压缩才能发送，而摘要、归档或提交失败 | 停止本次请求，保留已提交状态，给出可操作原因；不发送已知超预算请求 |
| HTTP/SSE 返回识别成功的上下文超限类型 | 当前模型请求最多压缩后重试一次，提高余量并要求实际缩减；第二次仍超限则显式失败 |
| 流式已向调用者发出可见 delta 后再报超限 | 第一版显式失败，不能把重新生成的内容拼接为同一答案 |
| 普通 400、认证失败、429、5xx、内容过滤、输出 `finish_reason=length` | 保持各自错误语义，不自动当作上下文超限；不引入无关重试策略 |
| 空摘要、工具调用摘要、截断摘要、无进展、过期候选 | 拒绝提交，保留原状态 |

新增 `ContextWindowExceeded` 类型，在 transport 层解析已知 provider 错误码/明确模式；普通含有 `length` 的字符串不够。未知容量或不受支持的 provider 错误分类无法提供可靠自动恢复，应准确报告能力缺失。

同一次主请求已主动压缩后又触发真实超限，最多仍只有一次恢复机会；如果没有剩余可压缩材料，立即失败。任何恢复都从当前消息视图重新构建模型请求，不回退业务回合，不重执行已完成工具。

真实超限后的估算余量校正按 endpoint/model/counter 配置身份保留到本次运行结束，后续主请求继续采用提高后的余量；身份改变时重新计算。若 provider 给出可信容量则收紧对应预算，否则恢复时至少额外预留 `0.10C`，并通过一次重试限制兜底；收紧后连保护内容都容不下则立即失败。该初始校正规则不保证适合所有 provider，应结合 usage 误差评测调整。

每次压缩的调用上限、每回合尝试上限、原运行 max_turns/deadline 共同限制总工作量。后续若允许无回合上限运行，必须同时引入独立的维护调用/费用预算，不能移除这些限制后留下无限压缩循环。

## 10. 可观测性与操作体验

新增 `context_compaction_start/end/failed` 事件，记录触发原因、来源边界、前后 token 估计、计数方式、摘要耗时/用量、归档 ID、失败类型与是否放宽软目标。事件不能因观察者错误改变运行结果，也不把完整材料泄漏到普通日志。

`/context` 展示容量来源、预算与估计占用、固定开销、最近压缩结果、累计摘要用量和归档空间；未知 usage 显示未知，不显示零。`/compact` 在 idle 时复用相同事务，可带重点提示但仍受摘要安全与预算约束。CLI 当前同步命令分派需要接入异步命令执行，不能在运行中的 event loop 里再次 `asyncio.run`。

自动压缩时显示简短的开始和结束状态，任务完成后继续正常答案流；用户取消沿用当前取消机制。一个合理的状态文本是“正在整理上下文，完成后继续”，附计数仅作为估计。

usage 在四种模式中都按 request ID 记录一次。兼容的 provider 才启用流式 usage 选项；去重最终 usage 帧，不对累计帧重复求和。未上报用量保持未知。请求账单记录与会话提交是否成功分离，失败的摘要也可能已产生费用。

一期复用主模型客户端生成摘要，维持既有所有权，不额外关闭借用客户端。后续选择独立摘要模型前，应比较约束保留质量、窗口能力与真实总费用，不能仅比较单价。

## 11. 可行性、交付边界与验收

可行性较高：共享状态机、脱离对象投影、配对校验、运行所有权和严格快照已具备。工作量为中等规模、跨模块改造；风险集中于预算准确性、用户回合内部切分、失败提交和摘要质量，并非摘要 prompt 本身。没有足够依据给出完成天数或成功概率百分比。

建议按可独立验证的顺序交付，但全部完成后才宣称上下文管理可用：

1. 完整请求预算、容量配置、类型化超限和四模式 usage，先使问题可见。
2. entry 身份、checkpoint、归档、v2 快照与纯规划器，固定数据与提交契约。
3. 四模式前台摘要、工具大结果投影、单次恢复和 CLI 操作，完成真实长任务验收。

后置：后台摘要、独立便宜模型、跨会话长期记忆/RAG、全量 transcript/崩溃自动续跑、终端源头完整输出落盘、语义检索、便携归档 bundle。未来 Group 通过服务接口使用单 Agent 上下文能力，不把 Group 状态塞入 Session。

实现时必须验证以下门槛，本次设计工作未执行这些测试：

- 四种运行模式具有相同压缩结果与恢复次数；工具批次配对始终合法。
- 同一用户请求连续多轮工具执行可跨至少三次压缩继续推进；不用新增用户消息触发清理。
- 中英文、代码/JSON、巨大 schema、小窗口、巨大用户输入、巨大工具结果和参数均有确定结果；所有主请求和摘要请求符合配置计数器预算，真实 provider 的估计误差另外评测。
- 摘要空白/超长/截断、调用超时、用户取消、归档写失败、配额耗尽、版本冲突、重复超限都不错误提交或无限循环。
- active 更新、history 缓存逐出、旧配置迁移及异常降级均不能直接丢弃消息；工作集被替换的内容可通过摘要来源查回归档原文，归档缺失时不能静默继续执行。
- 完成过的有副作用工具执行次数保持一次；流式已输出内容后不静默拼接重试结果。
- v1 导入和 v2 往返、重复文本、可复用 tool_call_id、失踪附件、分页查询与 clear/load/reset 语义正确。
- 长轨迹内存随活动工作集和有限缓存有界；磁盘遵守归档配额，不默默淘汰引用中的材料。
- 固定任务包含早期明确约束、关键文件、一次失败尝试和待办项，压缩后仍能完成。结构正确不等于语义正确，需独立检查约束遗忘与错误归因。

性能评测对比现有裁剪与新策略：普通回合额外网络调用必须为零；记录本地准备 CPU p50/p95、峰值内存、摘要次数/token/等待、主请求输入与缓存命中、端到端时间、超限和重复压缩率、任务完成及约束保留情况。先测基线，再设延迟和质量目标；本设计不预先宣称毫秒开销或成本下降比例。

## 12. 设计自查

本方案不将近期缓存称作完整历史，不用消息条数替代 token 预算，不把字符估计称为精确计数，不将摘要变成高级指令，不把磁盘附件写入称作已保存会话，不把工具源头已丢弃的输出称作可恢复原文。消息丢弃已被用户明确排除，不能通过兼容模式、缓存清理或失败降级重新引入。

推荐的能力边界是：在明确模型预算和资源配额内，Agent 能重复、安全地缩减工作上下文；失败时保持可解释的状态，用户能查回成功压缩所替换的已有材料。它不承诺无限上下文、无限磁盘、摘要无损或任意崩溃后的自动续跑。
