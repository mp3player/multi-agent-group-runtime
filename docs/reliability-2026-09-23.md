# Agent 长时运行可靠性审计

> Historical report: this records the pre-compaction stage on 2026-09-23.
> Current behavior and evidence are documented in [runtime boundaries](agent-runtime.md),
> [repeated acceptance](agent-repeated-acceptance-2026-09-24.md) and
> [closeout fixes](agent-closeout-fixes-2026-09-24.md).

本轮从 `23aa70c`、321 项测试的单 Agent 基线开始，检查异常、超时、工具副作用、
上下文超限和资源增长。用户明确要求将上下文摘要与压缩策略留待后续设计，本轮未实施。
Group 和前端归档不属于本次范围。

结论：发现并修复了会妨碍连续运行的实际故障，但当前版本还不能承诺无人值守地无限运行。
正常完成、受支持的异常退出及后续新请求已有离线回归；没有进行真实模型、多日持续负载验收。

## 已修复的问题

| 问题 | 原来的结果 | 修复与验证 |
| --- | --- | --- |
| 异步流在取消时进入等待型 `finally` | 已超时但持续 busy，下一次请求被拒绝 | 在原任务内给 deadline 引发的清理增加一次有限宽限取消；真实 LLMClient 离线 HTTP 流也有回归 |
| 同步流关闭时再次报错 | 清理错误覆盖模型原始错误 | 保留原异常、记录次要清理错误，验证显式 close 和再次运行 |
| 终端超时/中断 | 只停止 shell，子进程仍能继续写文件 | 独立 POSIX 进程组，TERM 后有限等待再 KILL；验证忽略 TERM 的子进程及 KeyboardInterrupt |
| 终端输出和文件长行 | 返回虽截断，读取时仍大量占用内存 | 两路管道持续排空、有界保留；文件分块读取/跳过/探测和 Unicode 续读 |
| 错误写入参数或编码失败 | 先截空旧文件，再报错 | 写前验证、同目录临时文件及原子替换；注入提交失败后旧内容仍完整 |
| 目录枚举、替换扩张 | 大目录或大替换产生大量临时数据 | 真正有界枚举，替换前按 UTF-8 字节计算结果大小 |
| 工具结果含非法 UTF-8 或过大 | 后续模型请求可能无法序列化，历史保留过大 | 运行边界转义非法字符并限制保留长度，保留原始成功/失败类型 |
| 审计 sink 出错 | 成功执行的工具结果可能丢失 | 普通 sink 错误独立计数，JSONL 可保存 surrogate；不改变工具结果 |
| 审计、用量明细持续积累 | 内存随每次调用增长 | 默认各保留最近 1000 条；审计 ID 连续，所有事件仍写 sink，用量汇总保持累计 |
| 可选 usage 数据/监控异常 | 有效模型回答被统计错误替代 | 普通监控错误隔离并暴露诊断；缺失 usage 不伪造零用量 |

独立审阅还发现并修复了两个本轮引入的兼容问题：Python 3.11+ 模型重建取消异常时的
timeout 分类，以及 CRLF 文本的多行匹配。文件替换继续采用原有 universal-newline 行为，
与 `read_file` 展示的内容一致。具体测试结果见[测试报告](testing-2026-09-23.md)。

## 连续运行与故障验收

[恢复测试](../tests/test_long_running_recovery.py) 使用实际 Agent、LLMClient 和离线
`httpx.MockTransport`，不调用真实供应商：

- 四种调用方式覆盖 HTTP 400 上下文超限、429、503 和连接中断。
- 错误发布 `run_end=error`、释放运行占用，不自动重试、不执行未获完整模型响应授权的工具。
- 上下文超限会持续失败，直到调用方显式清理活跃上下文；测试没有假设“再次请求就能解决超限”。
- 同一个 Agent 轮换四种调用方式执行 1000 个任务、2000 次模型请求；910 次完成，
  90 次在工具写入完成后发生模拟模型故障。写入总数恰好 1000，无自动重放。
- 每轮检查工具配对、busy 释放及 history/active/audit/usage 的配置边界；用量累计独立于明细淘汰。

这是有限次数的确定性验收，不是模型质量、真实网络稳定性或多日运行证明。

## 当前仍有的边界

1. **上下文容量没有完整方案。** 当前按完整用户回合做消息数软裁剪，保留当前任务；
   history 单独限量。消息数不是 token 预算，单条大消息、系统提示词、工具 schema、
   单个长任务都可能超出模型窗口。尚无模型窗口识别、输出预留、自动摘要或超限恢复策略。
   本轮按用户决定延期设计；错误可正确退出不等于能自动继续长任务。
2. **重试与恢复仍由调用方决定。** 429/5xx/网络错误显式传播；未增加自动退避或自动副作用重放。
   空闲快照能恢复对话，不能恢复崩溃时的在途操作，也不保证 exactly-once。
3. **超时是合作式的。** 默认单请求超时 120 秒、最多 20 个模型回合，整体 run timeout
   默认关闭。配置整体 deadline 后，异步模型在原任务内取消；deadline 清理和独立 `aclose()`
   各有自己的 250 ms 宽限。阻塞或反复吞取消的自定义代码不能强制终止，期间继续持有 busy，
   不放任后台模型任务与下一次运行并发修改会话。无 deadline 时，不给任意外部取消新增 watchdog。
4. **工具具有明确额度和平台边界。** 终端目前仅支持 POSIX；另起 session 的进程可能脱离清理组。
   同步工具和文件系统 I/O 仍可阻塞调用线程。写入保证原子可见性，不承诺断电持久化，
   append 的部分 OS 写入失败不是事务性的。额度详见[配置](configuration.md)。
5. **观测不是完整持久化系统。** JSONL 文件需要外部轮转/保留策略；普通 sink 故障独立暴露，
   但不能强制打断任意阻塞 sink。累计用量按 label 保存，label 应稳定；流式 usage 尚未采集，
   现有用量汇总只覆盖供应商实际提供的非流式数据。

现阶段可以继续建设 Agent 的基础能力。下一阶段长任务保障的核心仍是上下文预算、压缩后的
任务连续性及超限恢复设计；这需要单独讨论和验收，不能用扩大消息数上限替代。
